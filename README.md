# Qwen2.5-1.5B 线下餐饮意图识别 + 槽位抽取

基于 **Qwen2.5-1.5B-Instruct** 的 **QLoRA 微调**项目，面向「线下餐饮门店」场景的**意图识别 + 槽位抽取**，输出统一 JSON。

- **意图 9 类**：点餐/下单、预订座位、查询菜单、转人工、投诉/退款、会员/优惠、营业信息查询、排队取号、闲聊/其他
- **槽位 10 类**：菜品、数量、口味偏好、忌口、就餐人数、就餐时间、桌型、联系人/电话、门店位置、支付/优惠
- **输出格式**：`{"intent":"意图","slots":{"槽位":"值"}}`

## 快速开始（WSL2，8GB 笔记本 GPU）

```bash
# 1. 环境（Python 3.12 + CUDA12.1 torch，已内置阿里云镜像）
bash setup_wsl.sh

# 2.（如未生成数据）生成数据
python generate_data.py

# 3. QLoRA 训练（约 1~1.5 小时，4060/8GB）
python train.py

# 4. 评估困难测试集（真实泛化指标）
python inference.py --adapter ./output --data data/hard_test.jsonl

# 5. 单句交互
python inference.py --adapter ./output --interactive "帮我订明晚7点3个人包间"
```

断网下载模型请先设置镜像：`export HF_ENDPOINT=https://hf-mirror.com`

训练参数（`train.py` 默认值）：QLoRA 4bit nf4、LoRA r=16/alpha=32、lr=2e-4、3 epoch、max_seq_length=256、bf16。

## 数据策略

> 公开的「中文线下餐饮意图+槽位」专项数据集几乎没有，因此采用 **模板合成打底 + 口语变体 + 手写真实语料注入 + 槽位值归一化**。

- **模板合成**：9 类意图 × 槽位池随机组合生成主体，句式多样。
- **槽位值归一化**：每个槽位值分 **canonical（标准值，进标签）** 与 **variants（口语变体，进句子）**。让模型学会把「仨人 / 3位 / 三个人」都归一到「三位」。
- **手写真实语料**：注入 51 条口语化句子（倒装、省略、生僻说法），见 `generate_data.py` 的 `REAL_CORPUS`。
- **困难测试集**：`data/hard_test.jsonl` 共 20 条，刻意偏离训练模板，用于检验真实泛化（常规 test 因与 train 同源会虚高）。

数据量参考：**每类 250 训练条 + 50 测试条**，9 类均衡（合 2301 训练 / 450 模板测试）。

## 评估结果（困难测试集 hard_test.jsonl，20 条）

| 指标 | 初版（1838 条） | 扩写后（2301 条） | 精修提示词后 |
|------|------|------|------|
| 意图准确率 | 1.000 | 1.000 | 1.000 |
| 槽位 F1 | 0.480 | 0.833 | **0.894** |

意图判断已学稳（100% 泛化）；槽位抽取通过「归一化 + 口语语料 + 提示词列明槽位」从 0.48 提升到 0.89。

### 已知边界（重要）

1. **时间字段细节偶发丢失**：如 `下周五中午12点` → `下周五中午`，「12点」这类时间细节偶尔抽漏。属 SFT 自由文本归一化的结构性难点，真实系统常配【后处理归一化层】或额外补时间语料。
2. **多信号叠加偶发空输出**：如 `清淡点 + 别太油` 叠加时，偶发整条不吐。可通过约束解码或精简提示词缓解，属长尾。
3. **会自造 schema 外信息**：如 `喜欢大杯、加冰` 会额外吐 `份量=大`、口味=`冰镇`。**如果下游是固定 10 槽位的硬管道需校验过滤；若下游是宽松消费（给人看/LLM 再整理）则无害甚至更完整。**
4. **评估口径偏严**：槽位按「标准值精确匹配」计 F1，语义等价但字面不同的会判错，数字略低估真实可用性。

## 软硬件约定

- 本机训练：**Windows WSL2 + CUDA on WSL + 本地 4060（8GB）**，QLoRA 省显存，实测显存占用约 7.7GB。
- `setup_wsl.sh` 强制用 **Python 3.12** 建 venv（torch 2.4.0 只支持到 3.12，系统 3.13/3.14 会装不上 torch）。
- 笔记本注意：**训练务必插电 + 电源「最佳性能」**，否则功耗被限、速度骤降。此外「i/s 慢、功耗低、占用高」多为**显存接近 8G 上限时的显存分配器抖动**，非故障。

## 部署建议

- 推理侧建议加一层**输出校验+归一化后处理**：丢 schema 外 key / 非法值 → 词典/规则归一时间数量等自由字段。这是性价比最高的兜底，无需重训。
- 若追求结构化输出的强约束，可进一步接入**约束解码**，根治自造 key 问题。
- 真实上线前建议补充一小批**带精确时间的真实语料**，针对性改善时间字段长尾。
